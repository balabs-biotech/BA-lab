# BA Labs Domain Interpretation Framework v1

## Responsibility

The interpretation package consumes a validated BAL-JSON analysis and applies
one explicitly supplied domain profile. It does not collect data, calculate
environmental indicators, alter findings, or persist results.

Supported module identifiers are `mycology`, `greentech`, and `lab`.
They are routing namespaces, not claims that a biological profile is already
scientifically validated.

## Rule contract

Each rule matches all of the following:

- an exact canonical `variable_code`;
- an exact statistical finding status;
- every required context tag.

A match emits a typed `DomainSignal` containing profile and rule versions,
severity, stable signal ID, message/recommendation codes, biological context,
subject and environment IDs when bound, and complete source-finding and
source-observation lineage. The stable signal ID includes the biological
context ID so one finding interpreted in two cultivation contexts does not
collide.

Context tags are explicit inputs. Examples of possible future tags include
`stage:fruiting`, `crop:tomato`, or `substrate:straw`; the engine does not
infer them from weather data.

## Scientific boundary

No default biological thresholds or recommendations are shipped. A profile
must be provided by a separately reviewed configuration. The framework
cannot turn a generic statistical outlier into a claim of heat stress,
contamination, disease, or required intervention.

A rule's `recommendation_code` is only a stable reference to content managed
elsewhere. It is not free-form advice generated by the environmental engine.

## Isolation

The package depends on BAL-JSON contracts and has no dependency on Supabase,
Notion, the frontend, or provider adapters. A profile can be loaded and
evaluated independently for each biological module.

## Current limitations

- Profiles are supplied in memory; no profile registry or database persistence.
- No UI for profile authoring or approval.
- No biological validation of thresholds or recommendations.
- No cross-variable causal model or growth-stage model.
- No automated action execution.


## Biological context binding

The `contexts.biological` package represents a biological subject in a
specific cultivation or experimental context. It carries stable subject,
organization, location and environment-context IDs; domain and organism kind;
optional taxon, strain, cultivar and substrate codes; culture stage; production
system; explicit context tags; and a validity interval.

A biological context is not inferred from weather observations. It must be
registered by the application or supplied by a trusted workflow.

`validate_biological_context_for_analysis` checks tenant, location,
environment-context identity and overlap between the context validity interval
and the analysis date scope.

`interpret_analysis_for_biological_context` is the integrated public entry
point. It rejects a profile whose module differs from the biological domain,
validates the environment binding, and adds explicit tags such as
`stage:fruiting`, `strain:BA-P80`, `substrate:wheat_straw` and
`system:fruiting_chamber` to the profile evaluation.

The binding is intentionally one biological context to one environment
context. When a biological batch moves between rooms or systems, create
separate time-bounded context records rather than rewriting its history.
